Pace Acceptance SuiteThe Pace oracle must test \*\*counts and invariants only\*\*. It must not reimplement ranking.\### Day GridTest:`D = 1..14`\### Candidate Pool GridFor each D, include E values around:\- `0`\- `2D`\- `round-half-up(2.5D)`\- `3D`Include values immediately below and above important boundaries where practical.Example structure:| D | E family | Exact E | Expected assertion status ||---:|---|---:|---|| 1..14 | Zero | 0 | Await Pace contract where needed || 1..14 | 2D | `2\\\*D` | Await exact Pace target || 1..14 | 2.5D | round-half-up(`2.5\\\*D`) | Await exact Pace target || 1..14 | 3D | `3\\\*D` | Await exact Pace target |\### Pace InvariantsFor every approved Pace case verify:\- requested day count is preserved;\- total selected count matches approved Pace contract;\- no day has more than 3 places;\- distribution is balanced according to the approved count rule;\- selected IDs are unique unless contract explicitly permits otherwise;\- selected IDs come only from the supplied candidate set;\- repeated identical input produces the same digest/state where determinism is required;\- candidate input-order permutation does not change contract-significant output;\- no hidden provider refresh occurs during state-only mutations unless explicitly allowed;\- warnings match the approved semantics.\### Required Negative ControlA deliberately invalid result must be passed through the independent checker.The negative control must fail for at least one clear invariant, for example:\- duplicate selected ID;\- missing requested day;\- more than 3 places on a day;\- selected ID outside candidate pool;\- wrong total;\- invalid version transition.The negative-control result must be saved as evidence.\---\## 6. State-Machine Acceptance ModelThe independent QA state model tracks only externally observable state:\- `sessionId`\- `version`\- requested days\- selected place IDs\- pinned place IDs\- warnings\- timestamps relevant to expiry\- provider/FastAPI call count where observableIt must not reproduce production mutation algorithms.\### Core State Rules1\. Generate creates v1.2\. Successful committed mutation increments version exactly by +1.3\. Failed mutation leaves state/version unchanged.4\. Two writes using the same current version result in one committed transition only.5\. Independent sessions never leak state into each other.6\. Expired/restarted state follows the approved contract.7\. State-only mutations do not silently refetch provider data unless explicitly approved.\---\## 7. Mutation Coverage\### ReplaceVerify:\- targeted day changes only;\- unaffected days remain unchanged;\- candidate subset invariant remains true;\- global uniqueness remains true;\- failed replacement is atomic;\- version changes only on successful commit.\### RegenerateVerify:\- targeted regeneration scope only;\- unaffected days remain unchanged;\- pins remain preserved according to P0 decision;\- global Pace invariants remain valid;\- warnings remain valid;\- provider-refresh count follows approved behavior.\### PinVerify:\- server response is authoritative;\- requested pin is reflected only after successful server commit;\- version changes exactly once on success;\- stale/concurrent pin requests do not produce double commit;\- ordering assertion waits for P0.\### RemoveVerify:\- removed item disappears from committed state on success;\- resulting hole/replacement behavior waits for P0;\- no unrelated day changes unexpectedly;\- global uniqueness and Pace constraints remain valid;\- failure remains atomic.\---\## 8. Verdict Rule\### PASSRC may be marked PASS only when:\- every acceptance row has evidence;\- all P0-dependent rows have approved decisions and completed tests;\- required negative control fails as expected;\- all mutation/state/concurrency/Pace/TTL/restart/zero-refresh checks pass;\- mobile evidence is independently verified;\- exact RC SHA/environment are pinned;\- open Blocker count = 0;\- open Critical count = 0.\### FAILRC must be marked FAIL if any required acceptance invariant fails or any Blocker/Critical defect remains open.\### NOT READYUse `NOT READY` when the RC cannot yet be judged because:\- required feature implementation is not available;\- a required P0 decision is still unresolved;\- required evidence is missing.\---\## 12.
